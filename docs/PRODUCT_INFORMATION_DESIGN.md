> 2026-09-09 方針変更: 以下の自動取得・再配信設計は保留。現在は公式サイトへのリンクと利用者自身の使用記録を表示する方式へ切り替える。申請・契約・自動転載は進めない。

## 目的と境界

資材台帳から製品情報を確認し、実際に使った理由と一緒に翌年へ残す。
農薬の使用可否や散布時期を自動で指示・保証しない。公式データの利用照会と条件確認が済むまでは、本データの取得・再配信を開始しない。
今回は設計文書だけを追加し、アプリのコード、保存データ、PWA版番号は変更しない。

## 現在の実装との接続

| 現在の場所 | 確認した状態 | 追加方針 |
| --- | --- | --- |
| `assets/js/screens/materials.js` | 資材に登録番号を保存。除草剤には公式リンクと未取得表示 | 同じ資材カード内へ取得・詳細・更新導線 |

## 構成

```text
FAMICの配布データ（利用条件確認後）
  → 管理側の取得処理
  → 形式・件数・登録番号・適用行の検証
  → 版付きの製品データを公開（公開範囲は照会に合わせる）
  → アプリの「製品情報を取得・更新」
  → 登録番号・製品名・剤型を利用者が確認
  → 各利用者の端末へ保存

農作業・圃場・メモ → 既存の各利用者のローカル保存
                    → 共通製品データのサーバーへ送信しない
```

初期候補は「管理側で取得し、検証済みの版だけ公開する方式」。各スマホがFAMICへ直接繰り返しアクセスする設計は避ける。
配信方式は未決定。GitHub Pagesだけでは非公開配信を前提にできないため、知人限定が必要なら認証付きの配信先が必要。
公開リポジトリへ申請書・個人情報・APIキーをコミットしない。秘密情報が必要な取得処理はサーバー側で管理する。

## 画面案

```text
資材台帳 / 登録した製品
登録番号: XXXXX
製品情報: 未取得
[製品情報を取得]

取得結果の確認
登録番号 / 正式名称 / 剤型 / 登録情報の版
適用作物ごとの使用条件
原典更新日 / 取得日 / 出典リンク
[この製品で保存] [取り消す]

保存後
製品情報: 保存済み（確認日）
[製品情報を見る] [更新を確認]
```

一覧はコンパクトな状態表示のみ。適用条件の表は詳細で表示する。
登録番号なしなら入力へ誘導し、名称の類似だけで確定しない。番号と名称・剤型に食い違いがある場合は自動保存しない。
新しい版を取得しても確認前は既存情報を置き換えない。取消では保存状態を一切変更しない。

## 製品データ案

新しいサービスをUIから分離し、取得・検証・保存・履歴参照を扱う。以下は仮の名前であり、今回の型定義変更ではない。

- `productKey`: 提供元と登録番号の組。
- `revisionId`: 原典ファイル群と変換方式の版から作る不変ID。
- `registrationNumber`, `name`, `formulation`: 製品同定情報。
- `sourceUrl`, `sourceUpdatedAt`, `retrievedAt`, `publishedAt`: 原典と各時点。原典更新日が不明なら不明とし、取得日で代用しない。
- `sourceHash`, `transformVersion`: 原典ファイル群のハッシュと加工処理の版。
- `applications[]`: 適用作物・雑草等・使用量・使用時期・方法・回数・土壌等を一行の条件セットとして保持。
- `ingredientLimits[]`: 元データに含まれる有効成分の総使用回数条件。製品の回数と混同しない。
- `registrationStatus`: 根拠と確認時点を持つ。不掲載だけで失効と断定しない。
- `verifiedAt`: 利用者が製品を確認して保存した日時。

`verifiedAt`は共通配信する不変な製品版本体ではなく、端末内の確認記録に置く。再確認のたびに同じ版IDの内容やハッシュが変わらない構造とする。

「収穫何日前」という数値だけを抜き出して一般化しない。田植え後日数、雑草葉齢、作物、使用方法が一体となる条件を維持する。初期版は原文中心とし、解釈できない箇所をAIで補完しない。
登録データに含まれない作用機作・相性・抵抗性対策・効果保証は生成しない。メーカー資料等の追加は別途出典と利用条件を確認する。
「使用期限」は製品容器等の有効期限と、適用条件にある使用時期を分けて扱う。登録番号だけで手元の製品の有効期限を確定せず、未取得・不明とする。用量・使用時期・有効期限の自動取得は現行未実装。除草体系の初期値3年は任意の見直し目安であり、期限や必須の薬剤変更周期へ変換しない。

## 保存と過去履歴

- 製品情報の不変な版を専用コレクションへ保存し、資材は現在選択中の版IDを参照する。
- 作業保存時には、その時点で確認済みの版IDを任意で記録する。版の内容もバックアップへ含め、IDだけにならないようにする。
- 過去作業の登録後に初めて製品情報を取得した場合、それは「後から参照した情報」。使用当時の登録内容だったとは表示しない。
- 資材の登録番号を変えた場合は現在の製品参照を外す。過去作業が参照する版は変更しない。
- 最新情報への更新、作業の編集・複製・削除、資材削除、グループ一括入力それぞれで参照保持の方針をテストする。
- グループ入力は既存の単一作業記録を共有する構造を維持し、圃場数分の製品データを複製しない。
- 大きな全農薬データをローカル保存へ入れず、利用者が確認した製品・必要な版だけを保存する。
- 保存容量超過や取得失敗では既存データを保持。書込み成功後にだけ「保存済み」を表示する。
- 版IDが同じで内容が違うバックアップは自動上書きせず、競合として検出する。
- 作業のメモ・実使用理由だけを編集した場合は、元の製品版参照を保持する。新規作業への複製は新しい実施記録として扱い、旧版を現在も有効と推定しない。製品変更時は明示確認し、保存の取消では元の参照と記録を保持する。
- 過去版が欠けた場合は「参照版なし」と表示し、現在版で代用しない。作業と年度割当の参照時点を区別し、計画時点の版を実使用時点の版と見なさない。

## 現行コードの読み取り監査

2026-09-08時点。以下は将来実装への制約であり、製品情報機能の検証完了報告ではない。コードは変更していない。

| 対象 | 確認結果と必要な保護 |
| --- | --- |
| 資材・スキーマ | `normalizeMaterial`は既存の追加属性を保持するが、新しい製品情報型の妥当性や参照整合を検証する仕組みではない。`normalizeFieldWork`と`saveFieldWork`は明示項目のみを扱うため、版参照をUIに足すだけでは保存されない |
| 除草体系 | `assignProgram`は割当時点の工程・資材名・登録番号を複写し、旧割当を保持する。製品の適用情報全体を当時版として保存する機能ではなく、最新の資材情報から旧割当を再生成してはならない |
| バックアップ統合 | `mergeData`は既知のコレクションと指定した`meta`配列を統合する。新しい製品版配列を`meta`へ保存するだけでは、取り込み側にしかない版が統合されない。明示的な和集合・同一ID内容競合・参照欠落の検出が必要 |
| 旧アプリ・復元 | リリース前バックアップは件数制限があり、製品版の恒久保管ではない。旧アプリでの再保存は新項目を失う可能性があるため、旧版経由の往復を無条件に保証しない。移行前JSONと新しい版を含むJSONの保全、互換性検証を実装開始条件にする |

## 個人情報と公開境界

共通配信物は許諾範囲の製品情報だけから許可項目を選んで生成する。利用者の`materials`全体や`state.data()`を配信用JSONに流用しない。そこには仕入れ・在庫・翌年メモ、圃場・作業者・写真等の非公開情報が含まれ得る。
申請者の連絡先・回答メール・認証情報・実データ入りの検証画像は、リポジトリ、公開URL、CI成果物、配布ZIPに含めない。画面を隠すことやURLを知人だけへ伝えることをアクセス制御とは見なさない。
農作業記録を送らない設計でも、配信側のアクセスログにIPアドレス、取得時刻、要求した製品の識別情報が残る可能性がある。ログの項目・保持期間・閲覧権限を決め、利用者へ説明する。圃場ID・作業日・メモをURLや解析イベントへ載せない。
申請情報の送信承認と、アプリの一般公開・製品データ再配信の承認は別々に確認する。いずれも本稿の作成では承認済みにしない。

## 更新・失敗時

初期版は利用者が更新ボタンを押す方式。管理側の取得頻度はFAMICへの照会後に決める。
公式データは変更内容によって更新時期が異なるため、取得日だけをもって最新と断言しない。[公式の更新説明](https://www.acis.famic.go.jp/ddownload/)

| 状況 | 表示・処理 |
| --- | --- |
| 未取得 | 未取得。作業記録の保存は妨げない |
| 同じ版 | 保存内容は変更しない |
| 更新あり | 変更箇所と日付を確認後に保存 |
| 通信失敗・オフライン | 保存済み情報とその日付を表示 |
| 形式異常・件数急減 | 新版の公開を中止し、旧版を維持 |
| 製品が見つからない | 番号等の確認へ。別製品で置き換えない |
| 原典から消えた | 状態未確認と表示。履歴は消さない |

## 完了条件

登録番号違い・剤型違い・適用条件の取り違えを防止する。取得→確認→保存→再起動→作業保存→履歴表示→新版更新でも旧版を参照できることを検証する。
取消・通信失敗・不正データ・容量不足・古いJSONの復元・異なるJSONの統合でも既存記録を失わないこと。
360px・390pxとPC幅の実操作、独立監査、元データとの照合を行う。個人の記録が製品情報取得先へ送られないことも確認する。
